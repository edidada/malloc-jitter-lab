# Glibc tcache 与 Arena：概念、路径和实时性影响

本文说明 glibc `malloc`（ptmalloc2）中两个常被混淆的机制：**tcache**（线程缓存）和 **Arena**（堆分配区）。它们都服务于通用程序的并发吞吐量与平均性能，但都不提供硬实时场景需要的最坏时延保证。

## 一句话区分

| 机制 | tcache | Arena |
| --- | --- | --- |
| 所在层级 | 线程私有的小块空闲缓存 | 可被一个或多个线程使用的堆分配区 |
| 主要目的 | 避免小对象频繁进入共享分配器路径 | 降低所有线程争用单一全局堆锁的概率 |
| 常见快路径 | 当前线程从本地空闲链表取/还小块 | tcache 未命中后，在所属 Arena 中查找、切分或合并 chunk |
| 并发特性 | 正常使用时无需与其他线程争锁 | Arena 内部有锁；线程共享同一 Arena 时仍会竞争 |
| 实时性结论 | 命中通常很快，但缓存耗尽或尺寸不匹配会退化 | 缓解竞争，不保证无竞争，更不保证等待上界 |

可以把它理解为：tcache 是每个线程手边的一小盒常用零件；Arena 是车间里的一个料库。零件盒有货时拿得很快，盒子空了仍要进料库；多建几个料库能减少排队，但无法承诺任意时刻都不排队。

## 分配和释放的大致路径

下面是小对象的简化路径，实际细节会随 glibc 版本、请求大小和运行时状态变化：

```text
malloc(size)
  │
  ├─ tcache 命中：当前线程直接取空闲 chunk
  │                └─ 常见快路径
  │
  └─ tcache 未命中或 size 不适用
       └─ 进入/选择 Arena
            ├─ 获取 Arena 锁
            ├─ 从 bins 查找可用 chunk，必要时切分或合并
            └─ 空间不足时扩展堆或建立新的映射

free(ptr)
  │
  ├─ 适合 tcache：放回当前线程的 tcache
  └─ 否则：进入 Arena 的空闲结构，可能合并相邻 chunk 或触发归还内存
```

因此，`malloc`/`free` 的平均耗时不能代表控制周期的最坏耗时：一次请求是否命中 tcache、是否碰到竞争、是否需要整理或向内核申请内存，都会改变路径。

## tcache：为何很快，也为何不能作为实时保证

tcache 为每个线程保留若干常用大小类别的空闲 chunk。小对象反复分配和释放时，线程通常只操作自己的链表，避免 Arena 锁，因而平均延迟很低。

它仍不等于“零抖动”，原因包括：

- 每个大小类别的缓存容量有限；耗尽时必须回退到 Arena。
- 仅适用于一部分请求大小；较大对象或不匹配的大小仍走其他路径。
- 线程退出、跨线程释放、内存压力和 glibc 配置都会改变缓存命中情况。
- 即使某轮控制循环命中，下一轮也不能由业务代码保证仍然命中。

对实时代码而言，tcache 可看作偶然的性能收益，不能作为时延预算的前提。正确做法是由应用显式预分配并管理实时段所需对象。

## Arena：为何能提高吞吐量，却仍有锁竞争

早期单一堆在多线程下会让所有分配操作争同一把锁。ptmalloc2 引入多个 Arena：线程通常优先使用一个 Arena，竞争时可能尝试其他 Arena。这样能把高并发分配分散到多个锁上，提升总吞吐量。

但 Arena 不是线程独占堆：Arena 数量有限，线程数、生命周期和分配模式变化后，多个线程仍可能落到同一个 Arena。进入 Arena 慢路径时需要其内部锁；如果持锁线程恰好在做较重的分配、释放或被调度器延后，等待线程的延迟就会升高。

`MALLOC_ARENA_MAX` 或 `mallopt(M_ARENA_MAX, ...)` 可以限制 Arena 数量，用于诊断或控制内存占用。把它设为 `1` 往往会放大竞争，适合作为本项目 `02_arena_contention` 的对照；它不是实时系统的修复方案。

## 与优先级反转的关系

如果低优先级存储线程持有某个 Arena 的内部锁，而高优先级控制线程需要同一 Arena，高优线程会等待。若中优先级线程持续抢占低优线程，就可能形成优先级反转：高优线程实际被低优线程持锁和中优线程抢占共同阻塞。

应用层 `pthread_mutex` 可以选择 `PTHREAD_PRIO_INHERIT`，但不能把 glibc 内部分配器锁变成一个由应用控制的实时锁。因此，优先级继承是应用共享锁的缓解手段；控制路径彻底避免通用动态分配，才是更可靠的设计。

## 排查与工程建议

1. 先量化尾延迟：记录 P50、P99、P999 和最大值，而不只看平均值。
2. 使用 `strace -f -c`、`perf lock` 或火焰图确认尖刺期间是否出现 futex 等待、分配器函数或内核内存管理路径。
3. 在控制线程统计分配次数；理想目标是在稳定运行阶段为零，而不只是“绝大部分命中 tcache”。
4. 在进入实时段之前完成容器 `reserve`、对象池初始化和内存触页；实时段使用固定容量缓冲区或线程私有池。
5. 将 protobuf/lz4/MCAP 写入、日志格式化和大块临时对象放到非实时线程，并通过队列传递已预分配的数据描述符。

> 注意：tcache、Arena 数量和具体阈值均属于 glibc 实现细节，会因发行版、glibc 版本、环境变量和负载而变化。实验应关注“是否存在无界慢路径或共享等待”，不要把某台机器上的纳秒数当成通用保证。
